## Purpose

Classify expected growth, protect foreign-key integrity, define archive/rebuild concepts, and establish evidence gates before partitioning or extraction.

## Scope and volume classes

No row count, hot-data period, retention duration or capacity target is invented.

| Volume Class | Table Count | Meaning |
| --- | ---: | --- |
| LOW | 204 | Governed configuration/reference/low-churn records. |
| MODERATE | 5 | People, Registration and business growth. |
| HIGH | 16 | Event/delivery/interaction rows needing bounded access/index discipline. |
| VERY_HIGH | 0 | Reserved for evidence-proven exceptional growth; none assumed. |
| APPEND_DOMINANT | 8 | Chronological immutable/attempt/access streams. |
| MEDIA_METADATA | 11 | Metadata grows with external objects/processing. |
| PROJECTION | 6 | Rebuildable read model. |

## Core relational integrity boundary

Persons, Accounts, Organizations, Competitions, Registrations, Participant Snapshots, Judge Assignments, Score Sheets/Items, Results, Appeals, Certificates, Guardian Relationships and Consent retain ordinary InnoDB foreign keys and are not initially partitioned. Bounded indexes, pagination, read models, archival and evidence-led extraction come first.

## Partitioning candidates and restrictions

| Candidate | Initial Decision | Evidence Required |
| --- | --- | --- |
| Audit/security events | No initial partitioning | Retention, chain/checkpoint, FK impact, query ranges, restore/archive rehearsal |
| Notification/webhook attempts | No initial partitioning | Volume, state/time query, retention, reconciliation and operations |
| Feed/media access events | No initial partitioning; collection requires purpose review | Traffic, privacy retention, query, rebuild and isolation |
| Analytics/integration events | Prefer separate rebuildable/append boundary only after evidence | Source/checkpoint, replay, privacy and restore |
| Official relational tables | Prohibited initially | Equivalent integrity plus formal ADR/migration review |

MySQL 8.4 does not permit ordinary InnoDB foreign keys on user-partitioned tables. OD-069 owns the threshold; MySQL version/provider, query, retention, restore and archive tooling are prerequisites.

## Archive classifications

| Archive ID | Classification | Definition | Decision Dependency | Restore Procedure |
| --- | --- | --- | --- | --- |
| QMDB-ARC-001 | Hot authoritative | Current operational rows remain in primary InnoDB with full FK integrity. | Measured query/activity/retention policy | Normal backup/PITR |
| QMDB-ARC-002 | Warm historical | Closed but routinely queried versions remain read-only in primary schema or approved warm store. | OD-014/OD-037 and query evidence | Governed rehydrate with checksum/FK reconciliation |
| QMDB-ARC-003 | Cold evidence object | Large/rare evidence bytes move to private cold object class while MySQL identity/hash/hold remains. | OD-013/OD-060 | Restore by hash and verify metadata |
| QMDB-ARC-004 | Audit archive | Append audit segments move only with checkpoint continuity and approved verification. | OD-037/OD-060 | Restore ordered segment; verify chain/checkpoints |
| QMDB-ARC-005 | Operational event archive | Delivery/integration/security attempts archive after policy and reconciliation. | OD-037/OD-060 | Rehydrate bounded range with source identity |
| QMDB-ARC-006 | Projection rebuild | Read models are purged/rebuilt rather than archived as truth. | OD-070 | Replay sources and reconcile |
| QMDB-ARC-007 | Anonymized retained record | Approved personal fields transform while necessary official/provenance facts remain. | OD-041/OD-037 | Restore only if policy permits |

An active record remains primary. An archive retains identity, class, checksum, source/version, location, hold/status and restore evidence. Cold evidence retains a MySQL metadata/hash record. Historical access uses the same authorization, Workspace, privacy and audit controls. Restore stages isolated, verifies integrity/classification, reconciles relationships and performs a governed forward migration.
