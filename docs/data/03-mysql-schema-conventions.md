## Purpose

Define deterministic names, logical types, common-column boundaries, identifier strategy, state/taxonomy rules, JSON controls, concurrency expectations and lifecycle restrictions for future MySQL migrations.

## Scope

These are implementation conventions, not executable DDL. Symbolic precision and policy values intentionally block migration generation until their open decisions are approved.

## Naming

| Object | Convention | Example |
| --- | --- | --- |
| Tables | Lowercase plural snake_case; module ownership documented, no meaningless prefix | `score_sheet_versions` |
| Columns | Lowercase singular snake_case; foreign key is singular parent concept plus `_id` | `participant_snapshot_id` |
| Primary key | `id`; constraint `pk_<table>` | `pk_score_sheets` |
| Foreign key | `fk_<child>__<parent>__<ordinal>` | `fk_score_items__score_sheet_versions__01` |
| Unique constraint | `uq_<table>__<short_columns>` | `uq_score_sheet_versions__sheet_version` |
| Check constraint | `ck_<table>__<rule>`; globally unique in schema | `ck_score_items__raw_score_nonnegative` |
| Index | `ix_<table>__<purpose>`; unique indexes use `ux_` when not constraint-owned | `ix_outbox_events__claim` |
| Generated column | Semantic name ending `_key` or `_lookup_hash`, not implementation jargon | `active_lookup_hash` |
| Version | `version` for optimistic current records; `version_number` or domain-specific version for immutable lineage | `result_version` |
| Status | `status_code` or domain-specific `<concept>_status` | `sheet_status` |
| Boolean | Positive semantic name; avoid ambiguous `flag` | `is_primary` |
| Time | `*_at` for instants, `*_date` for dates, `effective_from/effective_until` for validity | `submitted_at` |
| Hash/signature/key | `*_hash`, `*_checksum`, `*_signature`, `*_key_id` | `document_hash` |
| External identifier | `<provider>_reference` or `external_reference`, never overloaded public ID | `external_reference` |
| Join table | Stable relationship nouns, composite uniqueness, no generic polymorphic owner | `role_permissions` |
| Projection | Purpose plus `_projection` or `_projections`; source version mandatory | `live_scoreboard_projections` |

All generated MySQL identifiers must remain within 64 characters. The migration generator shall deterministically abbreviate long names with a collision-checked hash suffix while preserving the manifest ID as the stable cross-reference. ADR-032 through ADR-034 record these proposals.

`P_SCORE/S_SCORE`, `P_PERCENT/S_PERCENT`, and any future money parameters are named logical parameters, not SQL syntax. Executable migrations cannot substitute values until OD-049/OD-050 or a future finance decision is approved.

## Common columns by table category

| Column | Apply when | Do not apply mechanically when |
| --- | --- | --- |
| `id` | Every relational table needs an internal clustered key | Never expose it as sole public reference |
| `public_id` | Aggregate/entity/case/job is externally addressed or asynchronously correlated | Pure joins, internal reference rows and contained immutable children |
| `workspace_id` | Every TENANT_OWNED/TENANT_CHILD record; optional only on documented oversight/system events | Global reference/governed identity without tenant ownership |
| `status` | Record has an approved state machine/current lifecycle | Append-only facts whose event type already expresses state |
| `version` | Concurrent mutable current aggregate needs optimistic comparison | Immutable append-only child with no update path |
| `created_at/updated_at` | Mutable records need creation and last-change evidence | Immutable events use authoritative occurrence/commit time; do not pretend they are mutable |
| `effective_from/effective_until` | Versioned configuration/reference validity | Facts with a single occurrence instant |
| `submitted/approved/published/revoked/superseded_at` | Domain transition exists | Unrelated tables |
| `superseded_by_id` | Direct lineage is safe and acyclic | Cross-aggregate polymorphic successor |
| `deleted_at/deletion_reason` | Approved ordinary removable record and active-key strategy require it | Score versions, Results, Appeals, Certificates, audit, Consent or Quran releases |

## Public identifier comparison

| Criterion | UUIDv7 | ULID-style |
| --- | --- | --- |
| Sortability | Time-ordered by standard UUID layout | Time-ordered by ULID layout |
| MySQL storage | Natural `BINARY(16)`; standard UUID ecosystem | `BINARY(16)` with custom encoding or 26-character text |
| URL readability | 36-character canonical text unless encoded | 26-character Crockford Base32 |
| PHP implementation | Requires reviewed UUIDv7 library/implementation | Requires reviewed ULID implementation and case rules |
| Index locality | Good when generated monotonically enough | Good when monotonic generation is correct |
| Case handling | Canonical lowercase text convention | Case-insensitive alphabet creates normalization decisions |
| Database round trip | Not required | Not required |
| Debugging | Broad UUID tooling | Shorter text but custom tooling more common |
| Security | Opaque, not secret and never authorization | Opaque, not secret and never authorization |

ADR-031 recommends UUIDv7 stored as `BINARY(16)` because it aligns with the standard UUID ecosystem and compact indexes. OD-047 keeps the selection open until PHP library, serialization, monotonicity, collision and operational evidence are approved. Internal keys remain `BIGINT UNSIGNED` under proposed ADR-030/OD-048.

## Status and taxonomy boundaries

- Stable technical states with a closed approved state machine use `VARCHAR(32)` plus a named `CHECK` and Domain enum/value object.
- Governed or extensible classifications use relational lookup/taxonomy tables.
- Historically meaningful taxonomies are versioned; consumers retain the referenced version/code.
- Workspace-configurable labels never confer permission and reference a stable governed semantic code.
- MySQL `ENUM` is not the baseline because governance/versioning and online evolution vary by domain.
- No single generic status or taxonomy table replaces domain relationships.

## JSON convention

Every JSON column in the manifest defines purpose, schema version, validation owner, mutability, checksum requirement, indexed extracted properties, size decision and sensitive-data restrictions. Allowed uses are immutable Ruleset/configuration definitions, versioned snapshots where relational facts remain addressable, provider response copies, event payloads, media-processing metadata, template rendering metadata and rebuildable projection payloads. People, authority, competitions, registrations, judging, Score Sheets, Results, Appeals, Certificates, Guardian Relationships, Consent and Permissions remain normalized. Frequently queried properties graduate to governed columns or generated/indexable extracts.

## Exact text and collation

The database/table default is `utf8mb4_0900_ai_ci` for ordinary user-facing search where appropriate. Canonical Quran text is stored separately with an exact binary collation candidate `utf8mb4_0900_bin`, a release/Reading identity and checksum; OD-054 requires qualified validation before migration. Search-normalized Arabic is a derivative under OD-055 and can never overwrite or validate canonical text. Cryptographic values and opaque identifiers use binary types/collation. Email/phone lookup uses approved normalized keyed hashes under OD-051/OD-052.

## Nullable uniqueness and active identity

MySQL permits multiple NULL values in a unique key, so history-preserving contact and soft-removal models use a deterministic `active_lookup_hash`/active key that is the normalized lookup hash only while active and NULL otherwise. A unique constraint prevents two active values while permitting inactive history. The executable design shall verify generated-column expression legality, encryption/normalization order, race behavior and backfill before use. Membership, Registration, Guardian, follow/reaction/bookmark and Certificate uniqueness use explicit scope/state keys rather than assumed partial indexes.

## Foreign keys and checks

Foreign keys are immediate and creation-order-sensitive; circular workflows are broken with dependency-ordered creation and later constraint addition, not by permanently disabling checks. Each referenced column list is a candidate key. Same-row checks cover non-negative exact values, ordered time ranges, positive versions/sequences and valid field combinations. Cross-row dynamic Ruleset bounds, monotonic versions, approval independence, capacity, graph cycles and state transitions also require application transactions, locks, reconciliation and tests.

MySQL 8.4 documentation confirms enforced CHECK support and that user-partitioned InnoDB tables cannot participate in foreign keys: [CHECK constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-check-constraints.html), [InnoDB partitioning limitations](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations-storage-engines.html).

## Transaction isolation and locking

ADR-037 proposes `READ COMMITTED` for ordinary application sessions to reduce long snapshot/gap-lock surprises, with explicit locking reads and stronger transaction patterns for authoritative transitions; OD-056 remains the approval gate because deployment topology, replication mode and workload evidence can change the choice. Regardless of default isolation, critical operations use primary reads, `SELECT ... FOR UPDATE`, optimistic versions, unique constraints, deterministic lock order, bounded transactions, classified deadlock retry and idempotency.

Queue-like consumers may use `SKIP LOCKED`; it is not suitable for general transactional truth because it returns an intentionally incomplete view. See [MySQL locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) and [transaction isolation](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html).

## Soft-deletion restriction

Generic `deleted_at` is limited to ordinary mutable records whose approved lifecycle genuinely means removal. Submitted Score Sheet Versions, final Results, Appeals, Certificates, Audit Events, Consent history, canonical Quran releases and Result Corrections use explicit `WITHDRAWN`, `REVOKED`, `SUPERSEDED`, `ARCHIVED`, `ANONYMIZED`, `CANCELLED` or `REMOVED` semantics as appropriate. ADR-040 captures this restriction; retention periods and legal/administrative holds remain unresolved.
