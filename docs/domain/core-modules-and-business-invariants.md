## Purpose

This document defines planned module ownership and the business rules that no layer, module, integration, administrator, or client may bypass.

## Scope and architecture

QMDB is a secure modular monolith implemented through Domain, Application, Infrastructure, and Presentation layers. MVC belongs to Presentation. Domain modules own concepts and invariants; Application coordinates use cases and transactions; Infrastructure implements persistence, queues, storage, integrations, and clocks; Presentation adapts HTTP, API, SSE, CLI/worker entry points, and views. Controllers and templates contain no SQL or authoritative business calculations.

Allowed dependencies below mean calls to published module interfaces, policies, queries, or events—not direct reads of another module’s private tables or classes. Conceptual event names document intent; P0-B02 and later event contracts must version schemas, tenant context, privacy classification, correlation, and idempotency.

## Ownership rules

1. A module changes another module’s owned state only through that module’s Application interface or an explicitly consumed event.
2. Reports, Search indexes, live scoreboards, caches, exports, certificates, and public profiles are projections/representations; they never become the owning source.
3. Tenant context, correlation, actor/service identity, authorization decision, and record version cross module boundaries explicitly where relevant.
4. Cross-module transactions are coordinated in the Application layer; asynchronous delivery uses the Transactional Outbox and idempotent consumers.
5. A module may refuse an invalid request without partially applying related state. Failure detail is safe for the caller and full enough in protected Audit Events for investigation.

## Invariant enforcement standard

Every later detailed requirement and implementation must identify which invariants it enforces, the authoritative layer, database constraints where applicable, authorization policy, failure response, Audit Events, and negative tests. UI prevention alone is never sufficient. Public identifiers, client totals, cached projections, integration credentials, and organization titles never replace server authorization or authoritative state.
